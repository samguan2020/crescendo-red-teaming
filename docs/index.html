Crescendo Red-Teaming

A personal research project automating a published multi-turn jailbreak tactic and running it against seven open-source LLMs in parallel, so their resistance to the same escalating attack can be compared side by side.

Built for authorized safety research and red-team evaluation of LLM safeguards — not for attacking models or services without permission.

How it works

One objective, evaluated the same way across every model

The tactic comes from Microsoft Research's Crescendo paper: start a conversation from an innocuous, educational angle, then escalate each turn by referencing the model's own prior reply — the thing most safety filters aren't watching for.

Submit objective

A target objective and a set of models go into an async AttackJob.

Plan the escalation

Gemini, acting as the attacker, is prompted with the Crescendo guideline and returns a JSON plan of escalating turns.

Run in parallel

Each target model gets its own turn-by-turn conversation; models run concurrently, turns run in order per model.

Judge every turn

Each response is classified into a verdict, not just scored pass/fail at the end — see below.

Architecture

Hexagonal core, pluggable everything — no frontend

This is a backend-only research build. The domain layer — AttackJob, Turn, Verdict, the engine loop — has zero framework dependencies. Gemini, the HuggingFace router, Postgres, and Redis are all adapters behind ports, so any of them can be swapped without touching the attack logic. Routes are exercised directly (curl, scripts, or the FastAPI docs UI) rather than through a UI.

Resilience

An attacker refusal never fails the run

The attacker model is itself an LLM and can decline to extend the plan. FallbackStrategy cascades through three strategies so the evaluation keeps going instead of erroring out.

GeminiPlanStrategy

Asks the attacker for a full JSON escalation plan up front, one prompt per round.

→

ReactiveStrategy

Falls back to generating the next prompt turn-by-turn if the plan can't be parsed.

→

TemplateStrategy

Falls back further to a fixed escalation template if the attacker model is unavailable.

Judging

Every turn gets classified, not just the ending

Refusals are backtracked out of the target-visible conversation history, so a reactive strategy can retry from a softer angle — a refusal mid-conversation doesn't dead-end the run.

REFUSAL

Model declined; excluded from what the target sees going forward.

COMPLIANT

Model answered within its safety boundaries.

NEAR_MISS

Model partially engaged without fully crossing the line.

JAILBROKEN

Model produced the targeted unsafe content.

ERROR

Transport or provider failure, judged separately from safety outcomes.

Engineering decisions

Choices made for an auditable evaluation, not a demo

Why hexagonal

The domain (AttackJob, Verdict, the engine loop) imports nothing from FastAPI, Gemini, or HuggingFace. Swapping the attacker model or adding a new judge doesn't touch the evaluation logic.

Why two stores

Postgres is the source of truth for the full trace — required for audit and export. Redis holds a read-only projection so a caller can poll a running job without hammering Postgres.

Why fail-fast settings

Required secrets (Gemini key, HuggingFace key, database URL) are validated once at startup. A misconfigured run fails immediately instead of erroring on the first real request.

Why backtracking

A refusal is recorded in the durable trace but removed from what the target model sees next, so a single refusal doesn't collapse the rest of the multi-turn attempt.
